SACP / Scalable Audit and Control Protocol

把 AI 工作变成可审计的回执。

SACP 不是 runtime，也不是 scheduler。它是一层很薄、但很关键的审计协议。 它的作用很直接：让“完成”变成可验证的记录，让“下一棒”变得明确，让“是否能发布”变成有证据可看的判断。

核心口号No receipt, no trust.
核心作用审计 claims、evidence、next owner、human boundary
适用场景长周期、多模块、多 agent、跨模型续接
设计原则小核心，扩展命名空间，profile 先行

项目是什么

这是一个开源协议项目，目标是为 AI 工作流提供统一的“工作回执”语义。 它关心的是：谁做了什么、依据是什么、下一步归谁、哪里必须停下来请人类确认。

协议 回执 证据 下一棒 不保证正确性

项目边界

SACP 不是执行引擎，不负责调度 agent，不存数据库，不替代框架。 它只定义可审计状态如何被表达、传递和复核。

它解决什么问题

问题
Agent 说“done”，但没有证据。
问题
多 agent 交接后，没人知道下一棒是谁。
问题
公开发布前，缺少人类批准边界。
问题
长任务中，局部完成被误认为全局完成。

没有 SACP 时

状态：模糊 证据：缺失 下一棒：不清楚
Done. All tests passed. Ready to publish.

这句话像完成，但不是可审计完成。它没有把证据、边界和接棒关系说清楚。

Receipt Chain 为什么重要

Receipt Chain 是 SACP 的一个可选 profile，面向长周期、多模块、多 agent 协作。 它不是 runtime，也不是 scheduler。它的作用是把 parent handoff、evidence、decision、stop rule 串起来， 让一个长任务在多次交接后仍然可以被审计、被接棒、被复盘。

一句话总结： SACP 不负责把 AI 做对，它负责让 AI 工作过程可追踪、可复核、可交接。

这一轮我们做了什么

  • 新增了 Receipt Chain 主文档和中英双语说明。
  • 补了多 agent 项目示例和研究发布示例。
  • 把 changed-source 重新工作规则同步到了 lifecycle、status codes、dirty cases 和 doctor prompt。
  • 新增了协议设计参考，明确借鉴 HTTP、Git、OpenTelemetry、MIME 和 RFC 风格规范语言。
  • 把扩展命名、canonical spelling、alias 规则钉死，避免外部实现抄乱。

项目总结

SACP 的价值不在于“更聪明”，而在于“更可审计”。它把 agent 工作从一串聊天记录，变成可以验证、可以接力、可以留痕的协议记录。 对长周期任务、多模块协作和多 agent 交接来说，这层薄协议比再加一个大 runtime 更有用。

最重要的设计选择是：核心保持小，增长放在 extensions 和 profiles 里，任何新想法先经过 dirty case 和 reference example，再考虑进核心。
